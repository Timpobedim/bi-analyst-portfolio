# 05 — BI-аналитик

Витрины и дашборды розничной сети: слой SQL-моделей с зависимостями и проверками, единый словарь метрик и четырнадцать самодостаточных HTML-страниц, собранных из одного склада.

Данные синтетические, но не произвольные: двадцать четыре полных месяца, двенадцать магазинов трёх форматов, 1 250 382 чека, 3 749 162 позиции. Экономика сети сведена так, чтобы выдерживать отраслевые ориентиры — маржа 23,5 %, фонд оплаты труда 13,0 % выручки, реклама 2,7 %, операционный результат 6,9 % до аренды и налогов.

## Как запустить

```bash
uv sync
uv run bi build          # сгенерировать данные и собрать витрины
uv run bi test           # прогнать проверки витрин
uv run bi metrics        # словарь метрик
uv run bi list           # список дашбордов
uv run bi all            # собрать все четырнадцать страниц
uv run bi dashboard rfm  # собрать одну
```

Дашборды открываются двойным щелчком: ни интернета, ни шрифтов со стороны, ни единой внешней загрузки.

## Общее решение: дашборд — это текст, а не архив

Взят приём, а не инструмент. От Power BI здесь остались слой моделей и словарь мер; выброшен формат, который нельзя ни открыть, ни сравнить.

- **Витрины — SQL с зависимостями и проверками.** Десять моделей знают, от чего зависят, собираются в топологическом порядке и несут с собой проверки: не пусто, ключ уникален, нет пропусков, ссылки ведут в существующие строки, значения в разумных пределах. Это то, что делает dbt, — на сто строк кода и без внешнего сервиса.
- **Словарь метрик один на все страницы.** Семнадцать метрик с формулой, определением и оговоркой «чего не учитывает». В `.pbix` меры живут внутри файла отчёта, и через полгода «выручка» на экране продаж расходится с «выручкой» на экране маркетинга. Здесь определения лежат в одном месте, а дашборды берут формулу оттуда.
- **Один склад на четырнадцать страниц.** Расхождение чисел между дашбордами было бы ошибкой, которую видно, — в портфолио обычно наоборот: каждый экран сделан на своём наборе, и вопрос «почему выручка разная» просто не возникает.
- **Страница — обычный HTML.** Открывается двойным щелчком, читается в системе контроля версий, весит килобайты, работает без интернета. Графики нарисованы своим SVG — несколько десятков строк на тип.
- **Есть дашборд про качество данных.** Такой страницы обычно нет, и зря: без неё любая цифра выглядит одинаково надёжной. На ней — результаты всех 24 проверок, свежесть данных и список известных ограничений, которые проверками не ловятся.

## Как проверялось

- **128 тестов**, ни один не ходит в сеть: генератор данных, слой моделей и его проверки, отрисовка, склад, реестр дашбордов и командная строка. Каждая из четырнадцати страниц действительно собирается в тесте, и в ней проверяется отсутствие `nan`, `None` и внешних загрузок.
- `ruff` и `mypy --strict` — чисто.
- Экономика сведена против отраслевых ориентиров, и это поймало три настоящие ошибки, которых тесты увидеть не могли: фонд оплаты труда, превышавший всю выручку; запас на 275 дней при норме 20–30; стоимость привлечённого заказа выше среднего чека.
- Вырожденные панели найдены и убраны: план, который не выполнял ни один магазин; кривая удержания, стоявшая на 100 % и обрывавшаяся; численность персонала, которая могла только убывать, потому что замен никто не нанимал.

## Не проверялось

- Данные синтетические. Сезонность, доли категорий и конверсии каналов подобраны по здравому смыслу и отраслевым диапазонам, а не выведены из реальной выгрузки.
- Страницы не открывались в браузере вживую: проверено, что HTML собирается, самодостаточен и содержит ожидаемые числа, но вёрстка на глаз не смотрелась.
- Поведение на данных другого масштаба (десятки миллионов строк) не проверялось: DuckDB такое тянет, но время сборки и вид страниц с сотнями магазинов не измерялись.
- Словарь метрик не связан с витринами программно: формулы в нём записаны текстом, и совпадение с SQL витрин держится на дисциплине, а не на проверке.
